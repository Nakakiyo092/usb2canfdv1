Although this firmware is not developed by a company,
it serves as one of such products that offers a casual way to connect to a single CAN FD network as a general‑purpose USB‑to‑CAN interface.


## Core values

1. Conpatibility with the LAWICEL CAN ASCII protocol
2. Simplicity - a human‑readable, less host coding, text‑based protocol
3. Reliability
4. Performance


## Difference

Although backward compatibility was prioritized, the following aspects were intentionally changed against the LAWICEL CAN Tools: CAN232 and CANUSB.

### Delete outdated commands

This project does not support polling via commands.
Incoming frames are reported to the host on a push basis.
For this reason, the `P`, `A`, and `X` commands have been removed, which are already dectated as outdated by LAWICEL.

### Automatic bus off recovery

Automatic bus‑off recovery can be useful depending on the application and CANUSB implements this feature.
However, there are use cases where a device to repeatedly generate bus errors is unacceptable, and in such cases this feature can be harmful rather than helpful.
As this project aims to provide a general‑purpose interface, automatic bus‑off recovery is not implemented.
If recovery is required, the host should reopen the channel as needed.
Accordingly, a flag indicating the bus‑off state has been added to the status report returned by the `F` command.

### Saving the timestamp setting

The `Zn[CR]` command itself has been modified so that it no longer stores its settings in non‑volatile memory.
If the host wants to ensure that its own configuration is applied, the best practice would be to issue the settings before each channel open.
For this reason, allowing `Zn[CR]` to write to memory with limited write endurance would unnecessarily shorten the device’s lifespan.
When persistent storage of settings is required, this functionality has been moved to the automatic startup mechanism provided by the `Q` command.
