Although this firmware is not developed by a company,
it serves as one of such products that offers a casual way to connect to a single CAN FD network as a general‑purpose USB‑to‑CAN interface.


## Core values

1. Conpatibility with the LAWICEL CAN ASCII protocol
2. Simplicity - a human‑readable, less host coding, text‑based protocol
3. Reliability
4. Performance


## Difference from the original products

Although backward compatibility was prioritized, the following aspects were intentionally changed against the LAWICEL CAN Tools: CAN232 and CANUSB.

### Delete outdated commands

This project does not support polling via commands.
Incoming frames are reported to the host on a push basis.
For this reason, the `P`, `A`, and `X` commands have been removed, which are already dectated as outdated by LAWICEL.

### Disable automatic bus off recovery

Automatic bus‑off recovery can be useful depending on the application and CANUSB implements this feature.
However, there are use cases where a device to repeatedly generate bus errors is unacceptable, and in such cases this feature can be harmful rather than helpful.
As this project aims to provide a general‑purpose interface, automatic bus‑off recovery is not implemented.
If recovery is required, the host should reopen the channel as needed.
Accordingly, a flag indicating the bus‑off state has been added to the status report returned by the `F` command.

### Store the timestamp setting to volatile memory

The `Zn[CR]` command itself has been modified so that it no longer stores its settings in non‑volatile memory.
If the host wants to ensure that its own configuration is applied, the best practice would be to issue the settings before each channel open.
For this reason, allowing `Zn[CR]` to write to memory with limited write endurance would unnecessarily shorten the device’s lifespan.
When persistent storage of settings is required, this functionality has been moved to the automatic startup mechanism provided by the `Q` command.


# Testing the device

Once the firmware is flashed to the device, it can be tested by connecting to a PC’s USB port.
When the device gets powered, the 2 LEDs (RX & TX) will blink rapidly 5 times in total.

Then start a serial communication software and configure it to use a carriage return as the line ending.
Then select the correct port, press `V` and hit enter.
The device will reply `Vhhss`, where `hh` is the hardware version and `ss` is the software version.

Now you know you have full contact with the device and can configure a CAN speed, open the CAN port and send and receive frames.
The RX and TX LEDs indicate when a CAN frame has been succesfully sent or received by the device.

Note that you must have at least 2 nodes (the device under test is counted as one) to send or receive CAN frames
and the CAN cable must be terminated at both ends with 120 ohms and use a proper twisted-pair CAN cable.


# Host application design guide

Always start each session (when your program starts) by sending 2-3 `[CR]` to clear any previous command or queued characters in the device
(since false or leftover characters may be present in the queue after power‑up or from a previous session).

Then check the version with the `V` command to ensure the correct device is used.

It is reccomended to close the CAN port with `C` before setting the CAN speed, because the current port status is unknown.

Next, set up the CAN nominal speed with the `S` or `s` command, and the CAN data speed with the `Y` or `y` command.
It is recommended to configure all available settings to your preferred values, as some old configuration values may still remain.
These include settings for nominal bit-rates (`S` or `s`), data bit-rates (`Y` or `y`), filter (`W`, `M` and `m`) and reporting (`Z` or `z`).

Then open the CAN port with `O`.
The device will now operate for both sending and receiving CAN frames.

Send frames using the `t` or `T` command, and wait for the response to confirm whether it was placed in the CAN FIFO transmission queue.
Incoming frames from the CAN bus will be sent out immediately to the host application.

Periodically send the `F` command to check for any errors (e.g. every 500-1000ms, or whenever you receive an error response from the device).
